Why this problem is different

The two framing insights

Your corpus is small, fixed, and sacred. The Qur'an is 114 surahs / 6,236 verses — it never changes. The Tafsir corpus is larger but grows slowly and is curated, not user-generated. This is the opposite of a typical GraphRAG problem. It means you can precompute almost everything, the entire graph fits in RAM, and concurrency is a read-scaling problem — not a write-scaling one.

You must architecturally separate the divine text from human interpretation. Qur'anic text and verified translation are immutable, verifiable facts. Tafsir is scholarly opinion — plural, sometimes divergent, always attributed. The graph and the generation layer treat these as different classes of truth. Conflating them is the single biggest doctrinal risk.

Every decision downstream — the storage call, the retrieval routing, the schema's truth-class tagging, the anti-hallucination gates — follows from these two facts. Because the corpus is fixed, the expensive work (triple extraction, embedding, entity resolution, deep thematic traversal) is pushed left, into an offline build run under human review, and never enters the request path.

System topology

Layered architecture

Four layers, cleanly split between request-time (cheap, bounded, cacheable) and build-time (expensive, offline, versioned, reviewed).

The critical move is pushing work into build-time. Request-time does only cheap, bounded work — an ANN lookup, a 1–2 hop traversal, a rerank — so latency stays flat under concurrent load.

Retrieval strategy

Balancing vector ⇄ graph under load

Don't run both engines on every query — route. A small classifier (or a fast, cached LLM call) tags query intent and picks a path:

Query shapeExamplePrimary path
Semantic / definitional"What does the Qur'an say about patience?" Vector-first → verses by similarity, then 1-hop to attached Tafsir
Relational / structural"Which verses does Ibn Kathir link to Ayat al-Kursi?" Graph-first → deterministic traversal, no vector needed
Thematic / comparative"How is the story of Musa told across surahs?" Hybrid → vector seeds entry verses, graph traverses links, fuse
Factual lookup"Show me 2:255" Direct index → skip retrieval entirely

Where the latency wins actually come from

  • Semantic caching at the edge. The same ~thousand questions cover most traffic. Cache on embedding similarity, not exact string — this deflects the majority of load before it touches retrieval.
  • Bound graph queries to 1–2 hops at request time. Anything deeper is precomputed at build-time as materialized paths. Deep live traversal under load is the classic GraphRAG latency killer — avoided by never doing it live.
  • Keep the graph in memory. At this corpus size the whole graph + vector index fits on one well-provisioned node. Scale reads with replicas, not sharding.
Confirmed for this build

Locked decisions

Storage

Single-store

Neo4j w/ native vector index, or Postgres + pgvector + Apache AGE. Graph + vectors co-located → hybrid retrieval is one query, fewest moving parts.

Concurrency

Hundreds

One in-memory node + a couple of read replicas + semantic cache covers launch comfortably. No sharding, no regional pods yet.

Doctrine

Plural + attributed

Surface multiple scholarly views, each cited to its source. The system attributes; it never arbitrates. Enforced in the schema, not just the prompt.

Migration path: if you outgrow single-store, the split is clean — the vector index lifts out to a dedicated engine (Qdrant/Weaviate) keyed by node id, while the graph stays put. Nothing in the schema below assumes co-location beyond the fusion query, which becomes a two-call fan-out.
Ontology · Part 1

Schema — four governing principles

  1. Truth-class is a first-class property. Every node is tagged canonical interpretive derived. The generation layer treats each differently; the schema forces the distinction.
  2. No anonymous assertions. Every interpretive and derived edge carries provenance — which source or extraction run asserted it, and a confidence. An unattributed doctrinal edge is a schema violation, not a quality issue.
  3. Closed predicate vocabulary. Relationship types are a fixed enum. The extraction LLM may only emit predicates from that list — open-vocabulary extraction over scripture is banned by design.
  4. Stable, human-readable IDs. ayah:2:255, source:ibn-kathir. Deterministic, so rebuilds are idempotent and diffable under review.
canonical

The Arabic text and verified translation. Immutable. Never LLM-touched.

interpretive

Tafsir & occasion-of-revelation. Plural, attributed opinion. Always cited.

derived

Machine-extracted topics, thematic links, embeddings. Carry a review_status.

Not every translation is canonical — the translation_type split

A literal (harfiyah) translation renders the words. An interpretive (tafsiriyah) translation renders the meaning as its author understands it, folding exegesis into the translated text. On 1:3 "Ar-Rahman Ar-Rahim", Kemenag gives "Yang Maha Pengasih, Maha Penyayang"; the Tarjamah Tafsiriyah gives "…belas kasih-Nya kepada orang mukmin, serta Maha Penyayang kepada semua makhluk-Nya" — an exegetical claim wearing a translation's clothes.

So: only literal translations may be canonical. Interpretive ones are opinion — they carry source_id + authority_tier, are always attributed, and may never be presented as the plain meaning of the verse. The gate literal_iff_canonical enforces this at build time; there is no override.

Why Word / Root earn their place: they unlock a query class pure-vector RAG can't touch — "every verse sharing the root ر-ح-م (mercy)", morphology, precise linguistic grounding. A genuine differentiator for an Indonesian Tafsiriyah audience. If launch scope is tight, model Ayah + Root first and defer full Word tokenization to phase 2.
Ontology · Part 3

Relationship vocabulary

Sixteen predicates — the entire set. The extractor's system prompt enumerates these and refuses anything else. [*] marks edges that carry provenance {source_id, confidence, review_status, extracted_by}.

canonical  Structural — deterministic, no provenance

(Ayah)       -[:PART_OF]->        (Surah)
(Word)       -[:IN_AYAH]->        (Ayah)
(Word)       -[:HAS_ROOT]->       (Root)
(Translation)-[:TRANSLATES]->     (Ayah)
(Ayah)       -[:PRECEDES]->       (Ayah)   // reading order, for context windows

interpretive  Attributed — provenance mandatory

(TafsirPassage) -[:EXPLAINS]->        (Ayah)              [*]
(TafsirPassage) -[:AUTHORED_BY]->     (TafsirSource)
(Ayah)          -[:HAS_CONTEXT]->     (RevelationContext) [*]
(Ayah)          -[:ABROGATES]->       (Ayah) {naskh_type}  [*]  // naskh — always cited
(Ayah)          -[:REFERENCES]->      (Ayah)              [*]  // cross-ref asserted by a source

derived  Machine-extracted — provenance + review_status mandatory

(Ayah)   -[:MENTIONS]->               (Entity) {mention_form} [*]
(Ayah)   -[:ABOUT_TOPIC]->            (Topic)  {weight}       [*]
(Ayah)   -[:THEMATICALLY_LINKED_TO]-> (Ayah)  {weight, basis} [*]
(Entity) -[:NARRATIVE_OF]->           (Entity) {role}         [*]
(Topic)  -[:SUBTOPIC_OF]->            (Topic)                 [*]

New predicates require a schema PR + scholar sign-off — never an ad-hoc LLM decision.

The doctrinal keystone

The provenance model

Every interpretive / derived edge is an assertion by someone or something:

(:TafsirPassage {id:'tp:ibn-kathir:2:255'})
  -[:EXPLAINS {
      confidence:    1.0,
      review_status: 'scholar_verified',   // human_pending | scholar_verified | auto
      extracted_by:  'curated_import_v3'    // or 'llm_extract_run_2026_07'
   }]->
(:Ayah {id:'ayah:2:255'})

This is what makes plural + attributed work structurally: a query for "the meaning of X" returns N TafsirPassage nodes, each with its source and authority_tier. The generation layer is contractually required to present them side-by-side with citations — it cannot collapse them into one voice, because the graph never gave it one.

Retrieval, concretely

The three modes, as queries

Vector-first — "verses about God's sovereignty"

CALL db.index.vector.queryNodes('ayah_id_embedding', 8, $qVec) YIELD node AS a
OPTIONAL MATCH (tp:TafsirPassage)-[:EXPLAINS]->(a)   // 1-hop enrichment, bounded
RETURN a, collect(tp)

Graph-first — "what does Ibn Kathir link 2:255 to?" (deterministic)

MATCH (:Ayah {id:'ayah:2:255'})-[r:REFERENCES|THEMATICALLY_LINKED_TO]->(a2:Ayah)
WHERE r.source_id = 'source:ibn-kathir'
RETURN a2, r.basis

Hybrid — "how is Musa's story told across surahs?"

CALL db.index.vector.queryNodes('entity_embedding', 1, $musaVec) YIELD node AS musa
MATCH (musa)<-[:MENTIONS]-(a:Ayah)-[:ABOUT_TOPIC]->(:Topic {label:'Prophetic narratives'})
RETURN a ORDER BY a.surah_number   // precompute as a build-time hot path
Guardrails

Build-time integrity — enforced, not hoped

  • Uniqueness on every id; Ayah count must equal 6,236, Surah must equal 114 — a hard gate on every rebuild.
  • Every EXPLAINS / ABOUT_TOPIC / THEMATICALLY_LINKED_TO edge must have non-null provenance → CI rejects the build otherwise.
  • No edge may connect a canonical node to a derived node without passing through an attributed (interpretive) edge type. You can't quietly attach machine opinion to scripture.
  • Every derived edge with review_status:'auto' is excluded from doctrinal query paths until promoted — it can inform ranking, never a cited claim.

Together these make your three hard requirements structural: plural-attributed (provenance on every interpretive edge), anti-hallucination (truth-class separation + review gates), and low-latency hybrid (embeddings only where searched, traversals bounded, hot paths precomputable).

PART TWO

The Triple-Extraction Pipeline

The machine that populates the graph. It runs offline, in batch, versioned, and gated by human review — never in the request path. Its whole job is to turn prose into attributed, schema-valid edges without ever letting the model assert something over scripture that a scholar hasn't confirmed.

The dividing line

Import vs. extract

Not everything is "extracted." Conflating these is the most common GraphRAG mistake:

DataClassHow it enters the graph
Ayah text, Surah structure, Word/Root morphology, verified Translations canonical Imported from trusted structured datasets (Tanzil, Quranic Arabic Corpus, KEMENAG). Zero LLM. Deterministic, checksummed.
Tafsir passages, Asbab al-Nuzul interpretive Imported as text, then extraction runs over them to produce edges. The passage text itself is never rewritten by the LLM.
Topics, entity mentions, thematic links, cross-references derived Extracted by LLM, then validated + reviewed.
The constraint that kills most hallucination

The LLM only ever reads canonical/interpretive text and emits typed edges pointing at it. It never authors node text. That single rule eliminates the largest hallucination surface before any prompt engineering begins.

01 · Ingest

Load canonical data first. Each Tafsir source is registered as a TafsirSource node with its authority_tier and madhhab before its passages are processed — so provenance has a target. Every passage keeps a stable id (tp:<source>:<surah>:<ayah>) and a content checksum.

02 · Chunk, verse-aligned

Chunk Tafsir along ayah boundaries, not by token windows. A commentary passage is already scoped to a verse — preserve that. Every extracted triple then gets a natural anchor (ayah_id) and natural provenance (source_id) for free, before the model runs. Range-scoped passages (commentary on 2:1–5) attach to each ayah in the range with a scope_span marker.

Stage 03 · the constrained call

Extraction

The model gets the verse + translation (canonical anchor), the Tafsir passage (the source being read), and a closed schema. It returns structured JSON only — forced via tool / response_format, so malformed output can't propagate.

System prompt shape

You extract knowledge-graph edges from Islamic exegetical text.
You may ONLY use these predicates:
  EXPLAINS · REFERENCES · ABROGATES · HAS_CONTEXT
  MENTIONS · ABOUT_TOPIC · THEMATICALLY_LINKED_TO · NARRATIVE_OF

RULES
  • For every edge you MUST quote the exact evidence_span from the passage.
  • If the passage does not support an edge, omit it.
  • NEVER infer a relationship the text does not state.
  • NEVER assert the ruling/meaning of a verse as fact — attribute it to this source.
  • If nothing is extractable, return {"edges": []}.

Output schema (per edge)

{
  "predicate":     "ABOUT_TOPIC",
  "subject_id":    "ayah:2:255",
  "object":        { "type": "Topic", "label": "Divine sovereignty" },
  "evidence_span": "His Kursi extends over the heavens and the earth",
  "confidence":    0.86,
  "source_id":     "source:ibn-kathir"
}

Two choices do the heavy lifting here:

  • evidence_span is mandatory. No span → the edge is discarded at Stage 04. This forces grounding and gives reviewers a one-glance audit: does this quote actually say that?
  • The object is a canonical id or a candidate descriptor ({type, label}) — the model shouldn't guess node IDs for entities and topics. Resolution happens deterministically at Stage 05.

Extraction runs per-passage, in parallel — embarrassingly parallel over a bounded corpus.

04 · Validate — pure code, zero LLM

Reject any edge that:

  • uses a predicate outside the whitelist;
  • has a subject_id that isn't a real canonical node;
  • has an evidence_span that isn't a literal substring of the source passage — this catches fabricated quotes, a direct hallucination check;
  • fails predicate type rules (e.g. ABROGATES must connect two Ayahs).

Rejections are logged with a reason, never silently dropped — the reject log is itself a quality signal for the next extraction run.

05 · Resolve & dedup

  • Entity / Topic resolution: map each candidate {type,label} to an existing node via embedding similarity + an alias table ("Musa", "Moses", "Nabi Musa" → entity:musa). Above threshold → link. Below → queue as a new-entity candidate for review; never auto-create doctrinally-significant entities.
  • Triple dedup: the same edge from the same source collapses to one. The same edge from different sources stays as separate provenance — that plurality is the entire point. Never merge across sources.
Stage 06

The review gate

This is where doctrinal accuracy is won or lost

Promotion from auto to scholar_verified is the only path an extracted doctrinal edge reaches a citable answer. Everything else in this document is scaffolding around this gate.

Conditionreview_statusIn doctrinal query paths?
Imported canonical / curated Tafsirscholar_verifiedYes
Extracted, confidence ≥ τ_high, non-doctrinal predicate (ABOUT_TOPIC, MENTIONS)auto No — ranking only
Extracted, doctrinal predicate (ABROGATES, HAS_CONTEXT, REFERENCES) — at any confidencehuman_pending No, until promoted
confidence < τ_lowhuman_pendingNo

The scholar-facing queue shows the edge, its evidence_span, the verse, and the source. The reviewer promotes, rejects, or edits. Every decision is written to an audit log (who, when, what). Doctrinal edges — ABROGATES especially, since Naskh is contested — are never auto-promotable, regardless of confidence.

07 · Load — idempotent, versioned

Upsert by stable id: re-running the whole pipeline produces the same graph, no duplicate edges. Each load is tagged with an extraction_run version + embedding-model version, so you can diff two runs ("what changed when we upgraded the extractor?") and roll back. Because IDs are deterministic, re-extracting one source touches only that source's edges.

Recap

Five hallucination barriers

Independent, in pipeline order — each one alone is defeatable; together they're the moat:

  1. LLM never authors node text (import vs. extract split) → can't fabricate scripture.
  2. Closed predicate vocabulary → can't invent relationships.
  3. Mandatory evidence_span, verified as a literal substring → can't fabricate a supporting quote.
  4. Confidence + doctrinal-predicate gating → uncertain or sensitive claims can't reach answers unreviewed.
  5. Scholar promotion gate + audit log → a human owns every doctrinal edge that becomes citable.

Retrieval then only ever pulls scholar_verified edges into cited context. auto edges influence ranking but are never quoted.

Decisions to pin before build

  • Extractor model tier — a strong model vs. a cheaper one at higher volume with heavier review. For a one-time bounded corpus, spend on the stronger model; you extract once.
  • Review capacity — plural-attributed doctrine means real scholar hours on the human_pending queue at ingest. Scope who reviews and their throughput: this gates launch.
  • Thresholds τ_high / τ_low — set empirically from a labeled sample of ~200 extracted edges once the extractor is wired.
PART THREE

The Scholar Review-Queue

The piece most likely to sink the project — and a staffing and governance problem wearing an engineering costume. Everything in Parts One and Two exists to protect the gate described here.

The reframe

The review burden, sized

The instinct is "40,000 extracted edges × human review = impossible, we'll never launch." That is only true if you review everything. You shouldn't. Rough volume for a four-source Tafsir corpus:

Edge classEst. volumeReview burden
Structural canonical (PART_OF, TRANSLATES, HAS_ROOT…) ~50k+Zero. Deterministic import, no LLM, nothing to judge.
EXPLAINS (passage → ayah)~25k Near-zero. The passage is already scoped to the verse by its source. Verse-aligned chunking makes this structural, not inferred.
ABOUT_TOPIC · MENTIONS · THEMATICALLY_LINKED_TO ~35kSampled audit only. These are auto — they influence ranking, never a cited doctrinal claim.
Doctrinal: ABROGATES · HAS_CONTEXT · REFERENCES ~1–3kFull dual review. This is the real queue.
New Entity / Topic creation~300–800 Full review — naming matters.

Naskh cases are famously bounded (classical counts range from a handful to a few hundred by school). Asbab al-Nuzul covers a few hundred verses. Cross-references run to the low thousands.

The must-review set is ~1,500–3,500 edges — not 40,000

That is the difference between "impossible" and "a few focused weeks." Every design choice below exists to protect this ratio.

The throughput unlock

Tiered review policy

TierApplies toGateCitable?
T0 — no reviewStructural canonical edges Deterministic import + CI count checksYes
T1 — dual scholar review ABROGATES, HAS_CONTEXT, REFERENCES, new Entity creation Two independent reviewers must agree; disagreement escalatesOnly after promotion
T2 — sampled audit ABOUT_TOPIC, MENTIONS, THEMATICALLY_LINKED_TO @ high confidence Review a random n≈300 sample; if precision ≥ threshold (~95%), the population ships as autoNo — ranking only
T3 — blocked Anything below τ_low, or any doctrinal edge not yet promoted—No

The T2 sampling move is what makes this tractable: a statistical guarantee over 35,000 edges from ~300 human judgments — and those edges are never quoted anyway. If sample precision comes in low, you don't review harder. You fix the extractor and re-run. Human review is not a patch for a bad extractor.

Governance

Who reviews — three roles, not one

  • Curator (ops, non-doctrinal). Triages the queue, kills obvious junk, dedups, fixes formatting. Cannot promote doctrinal edges. Exists to keep scholar time scarce and expensive.
  • Reviewer (credentialed — mufassir-trained ustadz). Promotes / rejects / edits T1 edges. The load-bearing role.
  • Scholar board (senior). Adjudicates reviewer disagreement, owns the predicate vocabulary, and signs off on the source list and authority_tier values.
The single most consequential decision in the system

Which Tafsir are in scope, and how they rank, determines every answer the platform will ever give. That is a board decision, made once, in writing — not something an engineer picks while wiring the ingest script, and not something an edge-level reviewer can drift.

Reviewer UX

The review card

The design goal is to turn a doctrinal judgment into a binary evidence check. The reviewer should never have to reconstruct context.

Three rules that carry it

  1. The claim is in plain language, never Cypher. The reviewer is a scholar, not a graph engineer.
  2. The evidence_span is highlighted in situ, with surrounding context. This is the payoff for making it mandatory at Stage 03 — it converts "is this theologically true?" into "does this quote say that?", which is fast and objective.
  3. Reject requires a reason code from a fixed taxonomy: evidence_doesnt_support · wrong_predicate · wrong_entity · source_misattributed · doctrinally_incorrect · duplicate · out_of_scope. The reason distribution is your extractor's bug report — a spike in wrong_predicate means the prompt's vocabulary boundaries are blurry.
Existential distinction

Two kinds of disagreement

Sources disagreeing is data, not conflict. Ibn Kathir and Al-Jalalayn reading a verse differently is expected and correct. Both edges are valid, both persist, each attributed. The queue must never ask a reviewer to pick a winner between two sources. If your UI has a "which is right?" button, you have built a fatwa machine by accident.

Reviewers disagreeing is a conflict. Two reviewers judging the same edge differently → auto-escalate to the board. No silent tie-breaking.

Track inter-rater agreement (Cohen's κ) as a first-class metric. A low κ does not mean you hired bad reviewers — it means your rubric is ambiguous, and the fix is to sharpen the predicate definitions, not to lean harder on the reviewers.

Protecting scholar hours

Decision durability across re-extraction

The trap: you upgrade the extractor, re-run the pipeline, and 3,000 human decisions evaporate. Avoid it by keying every decision to a stable semantic identity, not a run id:

decision_key = hash(subject_id, predicate, object_id, normalize(evidence_span))

On re-extraction:

  • Identical key → prior promotion carries forward automatically. Zero re-review.
  • Evidence span changed → back in the queue (the grounding changed, so the judgment must be re-made).
  • New edge → queue as normal.
  • Previously rejected key reappears → auto-suppressed and flagged: the extractor is repeating a known error.

That last rule is quietly important. It stops a re-run from resurrecting rejected content, and it turns the reject log into a permanent regression guard.

Shipping

Launch before 100% — prioritize the hot path

You do not need a fully reviewed graph to go live. Order the queue by expected query traffic:

  1. High-traffic verses first — Al-Fatiha, Ayat al-Kursi, Yasin, Al-Kahf, the last two juz, the common du'a verses. A small fraction of verses absorbs the large majority of queries.
  2. Then doctrinal edges on those verses, then the long tail.

Ship when the hot path is reviewed, and let coverage grow behind the live product. Which requires one thing to be built first:

Honest degradation — build this before launch

When a verse has no scholar_verified doctrinal edges, the system must not improvise. It shows the canonical text plus attributed Tafsir passages verbatim, and states plainly that the relational layer isn't yet verified for this verse. Silence is a valid, dignified answer here — inventing a connection is not. This fallback is precisely what lets you launch early without risk.

Accountability

Audit trail & metrics

Append-only, non-negotiable

{ edge_key, reviewer_id, decision, reason_code, note,
  prior_status, new_status, extraction_run, model_version, timestamp }

Immutable. Every citable doctrinal edge traces to a named human who approved it, and the evidence they saw. When someone eventually asks "who decided this?" — and on a Qur'anic platform, someone will — there must be an answer that isn't "the model."

What to do first

Run a 100-edge pilot before committing to any timeline. Take 100 real T1 edges, put two reviewers through the card UI, and measure: seconds per edge, κ, and the reject-reason mix. That single afternoon gives you (a) a real throughput number to staff against, (b) a read on whether your predicate definitions are sharp enough, and (c) an early precision estimate on the extractor.

Every number in this document is an estimate until that pilot replaces it with a fact.

PART FOUR

Serving & Concurrency

How the system stays fast under load — and, just as importantly, what not to build.

The reframe

The latency budget

Your bottleneck is the LLM, not the graph

At hundreds-concurrent, chat traffic is human-paced — a user sends a message every 20–60 seconds while active, so ~300 concurrent users is roughly 5–15 requests/second. Retrieval runs in 20–80ms. Token generation takes 2–5 seconds. Optimizing a traversal from 40ms to 10ms while the LLM burns 3,000ms is theatre.

Target: p95 time-to-first-token < 1.5s, full streamed response < 6s.

Where the wins are

The cache hierarchy

The structural gift again: the corpus is static. Cache invalidation — normally the hardest problem in RAG — nearly vanishes. Answers change only when the graph changes (a rebuild, or a scholar promotion), never because the world moved.

LayerWhat it storesHit behaviour
L0 — exact response cachenormalized query → full cited response Return verbatim. ~0 LLM cost.
L1 — semantic response cachequery embedding → cached response, ANN matched Return if cosine ≥ 0.95 (conservative)
L2 — retrieval cachequery → retrieved node-set (pre-LLM) Reuse retrieval, re-synthesize
L3 — materialized traversalsprecomputed paths inside the graph Not a cache — a build artifact

The cache key is the whole design

key = hash(normalized_query, lang, prompt_version, graph_version, model_version)

Because graph_version and model_version are in the key, a rebuild or model upgrade invalidates by construction — no purge job, no stale-answer bug. Old entries simply become unreachable and age out.

Hard guard on L1 — specific to this domain

Never let semantic matching cross an explicit verse reference. "Explain 2:255" and "explain 2:256" sit ~0.97 cosine apart and are different verses. Rule: if the query contains an explicit āyah reference, the reference must match exactly or it is a cache miss. A wrong-verse answer on a Qur'anic product is not a cache bug — it is a credibility event.

Domain-specific load

Devotional traffic & Ramadan

Qur'anic traffic is not uniform. It is head-heavy and calendar-correlated — and both facts are exploitable:

  • Head-heavy. Al-Fatiha, Ayat al-Kursi, Yasin, Ar-Rahman, the last juz, the common du'a verses. A small fraction of verses absorbs the large majority of queries.
  • Calendar-correlated. Al-Kahf spikes every Friday. Ramadan is a sustained multi-week surge — plausibly 10–50× baseline — with a further spike around Laylat al-Qadr. Prayer times shape the daily curve.
  1. Pre-warm the cache at build time. Generate and cache responses for the top few hundred expected queries before traffic arrives. Cold-start hit rate should be high on day one, not earned over weeks.
  2. Ramadan is a scheduled event, not an incident. Provision ahead of it, warm the cache for its query mix (fasting, night prayer, Laylat al-Qadr), and rehearse the degradation ladder. It is the most predictable load event you will ever have — treat it as capacity planning, not firefighting.
Build-time artifacts

Materialized traversals

The rule: if a traversal is >2 hops and matches a known query template, materialize it at build time.

  • verse → all Tafsir passages (every source) — the #1 hot path
  • verse → topics, verse → entities
  • topic → verses (the inverted index)
  • verse → thematically-linked verses (denormalized, weighted, top-K)
  • entity → all verses mentioning it, ordered (the full Musa narrative chain)
  • root → verses (powers the linguistic queries)
  • surah → context bundle (revelation type, themes, summary)

Each turns a multi-hop live traversal into a single-hop lookup. This is why deep traversal never appears in the request path.

Infrastructure

Topology — permission to under-build

Memory sizing. ~6,236 ayahs + ~25k Tafsir passages + entities/topics. Embeddings ≈ 60k vectors × 1024 dims × 4 bytes ≈ 250MB. Graph structure is small; Tafsir text 100–500MB. The entire corpus fits comfortably in 8–16GB RAM on a single node — the database never touches disk on the read path.

Writes happen only during a build or a scholar promotion, so the primary is nearly idle and replicas absorb all reads.

What NOT to build

No sharding. No multi-region. No custom vector index. No microservices. At this scale with a fixed corpus, a monolith plus a cache plus one in-memory database is the correct architecture — and you should feel good about it. Complexity here buys nothing and costs you velocity.

The actual wall

The real ceiling: LLM limits and cost

  • Provider rate limits (TPM/RPM) are your true capacity ceiling, not CPU. At ~10 rps with ~3k-token prompts that is ~30k input tokens/second. Check quota headroom before Ramadan, not during.
  • Cache hit rate is money. A 60% hit rate roughly halves the LLM bill. This is the highest-leverage number in the system — instrument it first.
  • Keep context tight. Top-K verses plus their Tafsir, not 50 passages. Prompt bloat costs latency and cost and answer quality, simultaneously.
  • Backpressure, don't error. If the provider throttles, queue with an honest "thinking" state and shed load down the ladder below.
Under burst

The degradation ladder

LevelBehaviour
0 — NormalFull hybrid retrieval + LLM synthesis
1 — WarmWiden pre-warmed cache coverage; serve more from L0/L1
2 — TrimDrop the reranker; tighten top-K
3 — Source modeSkip LLM synthesis. Return the structured, cited retrieval directly — canonical text + attributed Tafsir, rendered by template. Fast, cheap, and doctrinally safer than synthesis
4 — QueueHonest wait state with position, not an error page

Level 3 deserves emphasis. Because the graph already carries attributed, verified sources, "just show the sources, beautifully" is a genuinely good product experience — not a failure mode. Most RAG systems cannot degrade this gracefully, because they have nothing but the model. You do.

Never degrade by

Loosening doctrinal gates, dropping citations, or letting the model answer without retrieval. Those are not trade-offs — they are failures wearing a trade-off costume.
